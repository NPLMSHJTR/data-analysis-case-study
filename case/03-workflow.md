# 03 关键步骤与操作顺序

> 顺序错了，不是效率低一点，而是会返工。这一篇讲的是「为什么这一步必须在这一步之后」。

## 一、先给一张总顺序表

从空目录到两份可交付文档，实际走了这些步：

| 序号 | 做什么 | 产出 | 为什么不能提前 |
|---:|---|---|---|
| 0 | 确认数据能不能拿到 | 一个能跑通的请求 | 拿不到数据，后面全是空谈 |
| 1 | 建目录骨架 + 配置文件 | `config.py`、`data/`、`outputs/` | 路径散落各处后来会到处改 |
| 2 | 写采集，先只抓 1 页 | 25 条影片，验证解析对不对 | 一次抓 10 页再发现解析错，白等 20 秒 |
| 3 | 留档原始 HTML | `html_snapshots/` 10 个文件 | 解析逻辑改了不用重抓，这是省时间的关键 |
| 4 | 评论数据找替代方案 | 12,828 条，覆盖 141 部 | 直采失败，必须先解决数据源才能往下走 |
| 5 | 文本清洗 + 去重 | `reviews_cleaned.csv` | 脏文本会让后面所有判定失真 |
| 6 | **人工标注 300 条** | `manual_validation.csv` | **必须在这一步做，见下文第 4 节** |
| 7 | 内容有效性分级 | `reviews_labeled.csv` | 需要清洗结果 |
| 8 | 情感分析 | `reviews_scored.csv` | 需要分级结果（只对 A 类做精细分析） |
| 9 | 星级一致性判定 | `reviews_dual.csv` | 需要星级 + 情感分两个输入 |
| 10 | 方法对比实验 | `method_comparison.csv` | 需要双维度结果 + 人工标注 |
| 11 | Q1 / Q2 | `q1_*.csv`、`q2_*.csv` | 只需要影片数据，可与 6—10 并行 |
| 12 | Q3 被低估指数 | `q3_*.csv` | 需要影片情感均值（来自 8、9） |
| 13 | Q4 偏差分析 | `q4_*.csv` | 需要情感分与星级 |
| 14 | Q5 推荐 | `q5_*.csv` | 需要 Q3 的指数 |
| 15 | 画图 | 18 张 PNG | 需要全部结果 |
| 16 | 代码截图 | 10 张 PNG | 需要源码定稿 |
| 17 | 生成 Word / PPT | `.docx`、`.pptx` | 需要全部结果 |

**第 6 步是最容易被放错位置的一步。** 大多数人会把它放到最后「补一个验证」，
但它其实是整个项目的方向盘——没有它，你无法知道第 7、8 步做得对不对。

## 二、第 0 步：先确认数据拿得到

这一步只有一件事：发一个请求，看返回什么。

```bash
python -c "
import requests
r = requests.get('https://movie.douban.com/top250',
                 headers={'User-Agent': 'Mozilla/5.0 ...'}, timeout=25)
print(r.status_code, len(r.text))
"
```

结果分三种，对应三条完全不同的路：

| 返回 | 含义 | 下一步 |
|---|---|---|
| `200` + 正常 HTML | 可以直接抓 | 继续第 1 步 |
| `302` 跳 `sec.douban.com` | 触发了安全验证 | 不要绕过，找公开数据集 |
| 连接超时 / 拒绝 | 网络或环境问题 | 先解决网络 |

我遇到的是第二种。短评页一律 302，所以评论数据改用了 GitHub 上的公开数据集。

**这一步的价值在于：它用 5 分钟排除了一个方向。** 如果先写了一千行采集代码、
跑了半小时才发现全部被拦截，损失的不只是时间，还有已经围绕「自采数据」设计好的下游逻辑。

## 三、第 2—3 步：先抓一页，再留快照

### 先抓一页

解析逻辑（CSS 选择器、字段提取、类型串拆分）是采集里最容易出错的部分。
一次抓 10 页，中间任何一页解析失败，你都要重新等一遍。

正确做法是**先只抓第 1 页的 25 条**，肉眼核对三件事：

1. 数量对不对（25 条）
2. 字段齐不齐（排名、片名、评分、人数、年份、类型…）
3. 有没有明显的解析错位（比如年份里混进了时长）

确认无误后再放开到 10 页。

### 留 HTML 快照

```python
# 每页原始 HTML 存一份，文件名带页码
snapshot = RAW_DIR / "html_snapshots" / f"top250_start{start}.html"
snapshot.write_text(resp.text, encoding="utf-8")
```

这 10 个文件（总计约 3.4 MB）后来救了命。

原因很简单：**解析规则几乎一定要改。** 比如发现「类型」字段需要按优先级判定而不是取首词，
这时候如果没存快照，就得重新访问豆瓣 10 次；存了快照，几秒钟就能离线重跑：

```bash
python -c "from src.acquisition import rebuild_raw_from_snapshots; \
           df = rebuild_raw_from_snapshots(); print(df.shape)"
```

这条命令**不访问网络**，只读本地文件。改完解析逻辑用它验证，比重新抓取快两个数量级，
而且不会给对方站点造成压力。

> 这条经验可以推广：**任何一次性的外部数据获取，都要把原始响应存下来。**
> 存的是「响应原文」而不是「解析后的结果」，因为后者已经丢失了你可能需要的信息。

## 四、第 6 步：为什么人工标注要放在中间而不是最后

这是整篇里最反直觉的一条，值得单独说。

### 常见做法

```
清洗 → 分级 → 情感 → 一致性 → 出结果 → 写报告 → 最后补一个验证集
```

看起来合理：先把主线跑通，验证是补充材料。

### 实际后果

我在早期版本里就是这么做的，结果是：**报告写到第四章要算 F1，才发现手上的标注数据没法用。**

具体有两处：

1. 标注字段不全。只标了「内容是否有效」，没标「情感方向」。而方法对比要同时评价
   内容分级和一致性判定，缺一半就没法算。
2. 标注样本有偏。为了省事只标了短评论，结果长评论一条没覆盖，
   而长评论恰恰是分歧最大的部分。

这两处都需要重新标注，而标注 300 条是纯人力工作，没有捷径。

### 正确的顺序

```
清洗 → 【抽 300 条，人工标注】→ 分级 → 情感 → 一致性 → 方法对比
                ↑
        在这里就定下标注字段和抽样规则
```

**把标注前置，等于提前定义「什么叫对」。** 标注表里有哪几列，就说明你要评价哪几件事；
标注了多少类样本，就说明你的指标能覆盖到什么程度。

这件事在写代码之前做完，代价是几小时的标注；放到最后做，代价是返工。

### 标注表长什么样

12 列，300 行（`data/processed/manual_validation.csv`）：

| 列名 | 谁填 | 说明 |
|---|---|---|
| `sample_no` | 脚本 | 样本序号 1—300 |
| `review_id` | 脚本 | 关联 `reviews_dual.csv` |
| `movie_name` | 脚本 | 片名 |
| `rating` | 脚本 | 星级 |
| `quality_label` | 脚本 | 规则判定的 A/B/C/D/E |
| `quality_reason` | 脚本 | 规则给出的理由 |
| `text_length` | 脚本 | 文本长度 |
| `clean_text` | 脚本 | 清洗后文本 |
| `human_label` | **人** | 人工判定的内容质量 |
| `human_sentiment` | **人** | 人工判定的情感倾向 |
| `human_note` | **人** | 为什么不一致等备注 |
| `annotation_source` | **人** | 标注来源 |

前 8 列由脚本生成，后 4 列必须人填。**抽样可以用 `RANDOM_SEED=20261109` 复现，
但标注内容无法复现——这是这个项目里唯一不能靠重跑得到的东西。**

抽样策略是分层的：按质量类别、星级、文本长度分层，尽量覆盖更多影片。
实测 300 条覆盖了 143 部影片。

## 五、第 7—10 步：一条不能打乱的链

这四步首尾相连，因为每步的输入是上一步的输出：

```
03 内容分级  ──→ 04 情感分析 ──→ 05 一致性 ──→ 06 方法对比
   需要清洗结果      需要分级结果      需要星级+情感     需要双维度+标注
```

### 为什么情感分析要用分级结果

理论上可以对 12,828 条全部做情感分析。但实际只对 A 类（11,562 条）做精细分析，
B 类只进整体情感统计，C/D/E/X 不进。

原因：**对一条广告做情感分析，结果没有意义。** 广告文案可能充满「精彩」「震撼」，
强行判定会污染影片的情感均值。

### 为什么一致性判定必须晚于情感分析

因为它需要两个输入：星级（来自原始数据）和情感分（来自上一步）。
`gap = star_norm − sentiment_score`，情感分没有就算不出来。

这里有个陷阱：如果把一致性判定写进情感分析模块里，看起来省一步，
但会导致「改情感模型必须重跑一致性」的耦合被隐藏。分开写，依赖关系是显式的。

## 六、第 11—14 步：四个问题可以并行

Q1 到 Q5 之间不是串行的：

```
07 Q1/Q2  ← 只需要影片数据（top250_raw.csv），随时可跑
08 Q3     ← 需要影片情感均值（04、05 的下游）
09 Q4     ← 需要情感分与星级（04 的下游）
10 Q5     ← 需要 Q3 的指数（08 的下游）
```

Q1/Q2 只依赖影片层面的数据，不依赖任何评论分析结果。所以它其实可以在第 2 步之后就跑。

实际按 07→08→09→10 的顺序排，是因为这样输出文件按问题编号递增，便于查找。
从依赖角度，07 完全可以提前。

## 七、第 15—17 步：产物生成

### 图表（15）

18 张图由 `src/visualization.py` 生成，数据直接读结果 CSV，不硬编码。

图题按章编号（图 3-1、图 4-1…），和正文引用严格对应。这一步的坑是
**matplotlib 中文字体**——Windows 上一般没问题，Linux 服务器上通常一个中文字体都没有，
图里全是方框。解决方式见 [04 工具与命令](04-toolbox.md)。

### 代码截图（16）

10 张代码截图由 `src/code_screenshot.py` **从真实源码渲染**，不是手动截屏。

这么做的理由：手动截屏无法复现。代码改一行，截图就过期了，而你不会记得去重截。
用脚本渲染，改完代码重跑一次就同步了。

### 报告（17）

Word 和 PPT 放在最后，因为它们的每个数字都从结果文件读取。

`report_generator.py` 有 2,440 行，绝大部分是排版逻辑和数字填充。
这个长度看起来不合理，但它换来一件事：**改任何中间结果，重跑报告，数字自动同步。**

## 八、完整的一次运行

把上面所有步骤串起来，就是三条命令：

```bash
cd douban_top250
pip install -r requirements.txt
python main.py
```

实测输出（2026-11-10 22:55:35 开始）：

```

02_文本清洗             ok        3.63s

04_情感分析             ok       24.67s   ← 最慢，要逐条处理 12,828 条
```

**如果只改了某一处，不要重跑整条。** 按依赖关系挑最短路径：

| 改了什么 | 最少要重跑 |
|---|---|
| 一致性阈值 | 05 → 06 → 08 → 09 → 10 → 11 → 13 → 14 |
| 被低估指数权重 | 08 → 10 → 11 → 13 → 14 |
| 报告排版 | 13 |
| 图表样式 | 11 → 13 → 14 |
| 情感词典 | 04 → 05 → 06 → 08 → 09 → 10 → 11 → 13 → 14 |

最后一行说明了为什么情感分析放在 04：它是最上游的重计算环节，改它几乎要重跑一切。
所以情感词典应该尽量早定稿。
